# План разработки Aurora AI Hub

## Что уже готово

- [x] Проект создан на Qt/C++ и QML с Sailfish Silica.
- [x] Приложение собирается в RPM и открывается в эмуляторе Aurora OS 5.2.1.200.
- [x] Созданы базовые страницы интерфейса и структура модулей.
- [x] Репозиторий размещён на GitHub.

**Важно:** страницы пока не означают, что модели, чат и интеграция уже работают.

## Кто за что отвечает

| Участник | Отвечает за |
| --- | --- |
| №1 — Тёма | QML, чат, `AiClient`, потоковые ответы |
| №2 — Сеня | `llama.cpp`, `llama-server`, `RuntimeManager` |
| №3 — Лёва | `ModelManager`, импорт, каталог и скачивание GGUF |
| №4 — Даня | API для других приложений, AI-Заметки |
| №5 — Жорик | Проверка памяти и совместимости, тесты, RPM |

## Этап 1. Проверить, что всё технически возможно

**Все начинают параллельно.**

- [ ] **Сеня:** собрать и запустить `llama.cpp` на Aurora OS, получить ответ от маленькой GGUF-модели.
- [ ] **Жорик вместе с Сеней:** проверить RAM, скорость, ограничения запуска и упаковку движка в RPM.
- [ ] **Даня:** сделать два минимальных приложения и проверить передачу запроса и ответа через доступный IPC (например, D-Bus).
- [ ] **Тёма:** сделать работающий экран чата с имитацией потокового ответа, пока движок не готов.
- [ ] **Лёва:** реализовать импорт локального GGUF и список добавленных моделей.

**Встреча команды:** Сеня и Жорик показывают реальную генерацию; Даня показывает обмен сообщениями между приложениями. Если что-то не работает, команда выбирает обходной вариант до дальнейшей интеграции.

## Этап 2. Подключить модель к чату

**Начинается после подтверждения, что движок запускается.**

1. **Сеня + Лёва:** согласуют, как `ModelManager` передаёт путь и сведения о модели в `RuntimeManager`.
2. **Тёма + Сеня:** согласуете методы запуска/остановки, адрес локального сервера, формат HTTP-запросов и потоковых ответов.
3. **Сеня:** реализует `RuntimeManager` (запуск, остановка, готовность, ошибки).
4. **Лёва:** подключает выбор модели к `RuntimeManager`.
5. **Тёма:** подключаешь `AiClient` к реальному серверу и выводишь ответ по мере генерации.
6. **Жорик:** проверяет сценарий целиком и фиксирует ошибки.

**Готово, когда:** пользователь импортирует модель, выбирает её, запускает и получает настоящий ответ в чате.

## Этап 3. Подключить AI-Заметки

**Начинается, когда чат уже получает реальные ответы.**

1. **Даня + Сеня:** согласуют API, через который второе приложение будет обращаться к модели.
2. **Даня:** реализует API и минимальное приложение AI-Заметки с действием «Сократить текст».
3. **Даня + Тёма:** согласуете отображение состояния AI и ошибок, если это требуется в основном приложении.
4. **Жорик:** проверяет IPC, разрешения Aurora OS и работу двух приложений одновременно.

**Готово, когда:** из AI-Заметок можно отправить текст и получить сокращённую версию через Aurora AI Hub.

## Этап 4. Довести проект до MVP

**После успешной интеграции всех основных частей.**

- [ ] **Лёва:** каталог моделей в JSON, скачивание с прогрессом, проверка файлов, удаление моделей и обработка нехватки места.
- [ ] **Тёма:** закончить страницы моделей, каталога, чата и настроек; добавить загрузки, ошибки и отмену генерации.
- [ ] **Сеня:** обеспечить надёжный запуск и остановку движка, обработку ошибок и освобождение памяти.
- [ ] **Даня:** завершить AI-Заметки и описать публичный API.
- [ ] **Жорик:** выполнить интеграционные тесты, проверить RPM-валидатор, установку и запуск на реальном устройстве.
- [ ] **Все:** обновить README, документацию и результаты тестирования.

**MVP готов, когда:** модель можно импортировать или скачать, запустить локально, использовать в чате и вызвать из AI-Заметок. RPM устанавливается и работает на выбранном устройстве.

## Как работать в GitHub

1. На каждую отдельную задачу создаём **Issue**, назначаем ответственного и указываем этап.
2. Каждый работает в своей ветке `feature/...`, не напрямую в `main`.
3. Перед изменением общего интерфейса модулей согласуем его с участниками, которые этот интерфейс используют.
4. Законченную задачу отправляем через **Pull Request**. Другой участник проверяет код и тесты.
5. После изменения функциональности обновляем `docs/STATUS.md` в том же PR.
6. Если проверка этапа не пройдена, не считаем зависимые задачи готовыми.

## Коротко: кто с кем согласуется

| Когда | Кто | Что согласовать |
| --- | --- | --- |
| Перед подключением модели | Лёва + Сеня | Выбор GGUF и передача пути к модели |
| Перед реальным чатом | Тёма + Сеня | HTTP API, потоковые ответы, ошибки |
| Перед AI-Заметками | Даня + Сеня | Межприложенческий API и доступ к движку |
| При каждом объединении | Автор PR + Жорик или другой участник | Сборка, тесты, совместимость |

Не нужно ждать завершения предыдущего этапа, чтобы готовить независимую часть своей работы. Но соединять модули следует только после согласования их интерфейсов.
